# CEO Plan: Central Brain (hexxu)

Generated by /plan-ceo-review on 2026-05-30

## Problem framing

Workers use pi as their daily-driver agent harness. Developers (currently solo)
use Claude Code in parallel for skill and tool authoring. We need shared
substrate so the dev↔worker loop compounds: a central place for skills, a
trajectory toward shared data and shared files, and the discipline that keeps
the door open to a fully self-hosted "Hexxu Platform" 12-24 months out.

The premise we explicitly tested: build vs. assemble vs. buy. The decision was
**minimal build now, with a 24-month trajectory toward selective self-hosting
as specific pain emerges.** The trap to avoid is shipping a full platform
ahead of worker traction.

## Vision

### 10x Check
The skill catalog is the product. Files and postgres are commodities.
Maximum 10x leverage = a worker→dev feedback loop that compounds skill
quality every week, paired with telemetry that grades skills by real use
rather than vibes. At 12 months, "new worker onboards" is a `npx hexxu`
command and they're equipped with 30+ shipped, owned, evaled skills.
At 24 months, the skill registry is a service (not just a git repo),
postgres holds session telemetry and shared business data, files live in
self-hosted S3, and pi extensions for all three are mature.

### Trajectory: A → B → C (not A → C as a project)

- **A (now, ~1 week):** Skills-First Lake. Central git repo for skills, workers' pi pulls.
- **B (weeks 2-7, as demand emerges):** Federation. Pi extensions for Drive/Notion (files), Supabase (postgres). All three pillars covered via SaaS.
- **C (months 3-24, piece by piece):** Selective self-hosting where SaaS cost or compliance demands it. Never a discrete project.

### Seven design constraints to keep A→C open (constraint #4 absorbs the manifest schema)

1. Skill versioning lives in SKILL.md frontmatter, not in git tags.
2. Worker identity is session-scoped, not skill-scoped. No skill reads `git config`.
3. Skill registry URL is configurable in pi config; never hard-coded.
4. **Skill manifest schema (authoritative spec).** Every skill's frontmatter carries: `name`, `description`, `version` (semver), `owner` (UUID matching `HEXXU_WORKER_ID`), `last_reviewed` (ISO date), and `requires` (optional array of `extension:<name>` or `data:<scope>` deps, e.g. `["postgres:hexxu_main", "files:hexxu_drive"]`). All five existing skills get retrofitted in a grandfather migration commit (see Implementation order step 4a).
5. Offline-first: skills cache locally and degrade gracefully when registry unreachable.
6. Permission checks happen in extensions at the data layer, not in skill logic.
7. **(new, from D3.1)** Identity contract: `HEXXU_WORKER_ID` env var, UUID format (v4), injected by the onboarding flow (CLI later, manual now). Every extension and skill reads identity from this single source. **Rotation policy:** a compromised or replaced UUID is treated as a new worker — old telemetry stays bound to the old UUID, no cross-linking.

## Accepted Scope (added to this plan)

- Central git repo `hexxu/skills` on **GitHub** (per Q1 answer), **public** (per Q3 answer), with the five existing skills + CLAUDE.md documenting the seven design constraints.
  - **Branch protection on `main` from day 1 (D5.2):** require PR + 1 approving review, no direct push.
  - **`docs/` directory from day 1 (Section 10):** stub files for `architecture.md`, `onboarding.md`, `extension-authoring.md` — solo-developer SPOF mitigation.
  - **`CONTRIBUTORS.md`** with documented trigger: "When this file has > 1 entry, revive the eval-gate TODO in TODOS.md."
- **Pi extension `hexxu-skills-sync`** that pulls the repo into `~/.pi/agent/skills/` on session start.
  - **Non-blocking:** sync failures WARN to stderr; pi session starts using cached skills.
  - **Cold-start (no cache + GitHub unreachable):** fail open with empty skills + visible warning, NOT fail closed (consistent with constraint #5).
  - **Sync staleness cache:** skip git fetch if local cache is < 5 minutes old (avoids thrashing GitHub at high session rates).
- **Identity contract:** `HEXXU_WORKER_ID` env var, UUID v4 format. Documented as constraint #7. **Portable across machines** — worker carries the same UUID to any box they pi from, so telemetry correlates. Manually set per worker for now; CLI later.
- **Identity drift CI check (D5.1):** GitHub Actions workflow greps PR diffs for forbidden identity sources (`git config user\.`, `\bwhoami\b`, `\$USER`, `\$LOGNAME`) and fails the check if any match. Enforces constraint #2 mechanically.
- **Telemetry extension** `hexxu-telemetry` listening for `session_shutdown` events, writing JSONL locally.
  - **Locked schema (additions are forward-compatible, removals are not):** `event_at` (ISO 8601), `worker_id` (raw UUID, local-only), `session_id`, `skills_invoked` (array of `{name, version}`), `duration_ms`, `exit_reason`. Implementer may add optional fields.
  - **File permissions:** mode 0600 on write.
  - **Append safety:** writes use `O_APPEND`; events kept under 4KB so POSIX guarantees line-atomic appends with parallel pi sessions on the same box.
  - **Rotation policy:** rotate when JSONL > 50MB OR > 90 days, whichever first; old files named `telemetry-YYYY-MM-DD.jsonl.gz`.
- **`hexxu telemetry-summary` CLI (D5.3):** reads local JSONL, prints `{skill: invocations, p50_ms, p99_ms, exit_reason_dist}` for a time window (`--since 7d` default). Foundation for the postgres-backed dashboard later.

## Deferred to TODOS.md (with context)

- **Eval-gate at merge time (CI on skills repo)** — GitHub Actions workflow that blocks merges of skill PRs unless the skill-creator eval suite passes. **Add when 2+ contributors exist.** **Why deferred:** at solo stage the gate adds friction without the cultural-norm payoff that makes gates valuable on multi-contributor repos; a solo contributor reviewing their own PR runs evals locally anyway. **Implementation when revived (design already worked out, no re-thinking needed):** pass threshold = skill scores ≥ 0.8 averaged across 3 deterministic seeded runs, no flake retries; per-PR cost cap via `max_eval_budget_usd` (default $0.50) with FAIL on overrun; eval results published to `evals/results/<skill>/<pr-sha>.json`; estimated cost ~3h workflow + ~1h secrets/cost-cap plumbing.
- **/skill-feedback worker→dev channel** — pi extension + queue file in skills repo. Add once 2+ workers are actively using skills. **Why deferred:** the loop is currently dev↔dev (solo); the channel is load-bearing only when there are workers separate from the dev. Pre-build risk: queue with no submitters loses signal.
- **CHANGELOG.md per skill** — convention/process. Add when 2+ contributors. **Why deferred:** process overhead without team.
- **`hexxu` onboarding CLI** — npx-installable scaffolder. Add when first non-you worker onboards. **Why deferred:** the marginal benefit is worker #2 onwards.
- **`/skill-search` slash command** — discovery aid. Add when skill catalog > 15. **Why deferred:** at 5 skills you remember them all.
- **Skill compatibility matrix** — `requires: pi >= X.Y` enforcement. Add when pi versions diverge across worker machines. **Why deferred:** not an issue at single-developer scale.
- **Postgres extension for telemetry aggregation** — first piece of pillar 2. Add when local JSONL is the bottleneck for skill analysis. **Why deferred:** local JSONL is fine until you want cross-worker queries.
- **Files extension (Drive/Notion read)** — first piece of pillar 1. Add when a specific worker workflow demands shared documents. **Why deferred:** no workflow demanding it today.

## Risks (carry to subsequent review sections)

1. **Worker non-adoption:** the plumbing works but workers don't use pi. Mitigation: skill quality + onboarding investment in the deferred items.
2. **Skill rot:** skills land, drift, decay. Mitigation: manifest's `last_reviewed` field + accepted ownership metadata + the deferred eval-gate (revived when contributors arrive).
3. **Identity drift:** ad-hoc identity assumptions sneak in despite the contract. Mitigation: **identity drift CI check (D5.1) enforces constraint #2 mechanically** — RESOLVED.
4. **Telemetry privacy:** worker_id + skills_invoked is sensitive once team grows. Mitigation: local-only for now (mode 0600); defer aggregation until policy is set.
5. **Skill quality drift without an automated gate:** without the eval-gate, a solo author can ship a skill that regresses against its own eval set. Mitigation: pre-commit hook recommendation (operational decision) + the deferred eval-gate is on the TODOS list for the moment a second contributor joins.
6. **Prompt injection via committed skill:** skills are loaded into pi system prompts. Compromise of any GitHub account with write access = code execution on every worker. Mitigation: **branch protection on main (D5.2)** requires PR + review for any merge — RESOLVED for solo + multi-contributor stages; revisit if branch protection is bypassed for emergencies.
7. **Telemetry exists but no one looks (observability rot):** classic "we have logs but nobody reads them" failure. Mitigation: **`hexxu telemetry-summary` CLI (D5.3)** makes the data trivially accessible day 1.

## Implementation order (proposed; revisit in eng review)

1. Set up `hexxu/skills` GitHub repo (public), enable branch protection on `main` (D5.2: require PR + 1 approving review), add the five existing skills + repo CLAUDE.md documenting the seven design constraints + `docs/` directory stubs + `CONTRIBUTORS.md` (~30 min)
2. Add identity drift CI check (D5.1): GitHub Actions workflow that greps PR diffs for forbidden identity patterns (`git config user\.`, `\bwhoami\b`, `\$USER`, `\$LOGNAME`) and FAILs on match (~30 min)
3. Write `hexxu-skills-sync` pi extension: non-blocking, cold-start fail-open, 5-minute staleness cache (~3 hours)
4. Define manifest schema as a simple .md spec under `docs/manifest-schema.md`
4a. **Grandfather migration commit:** retrofit existing five skills with new frontmatter fields (`version`, `owner`, `last_reviewed`, `requires`). One-time backfill. (~1 hour)
5. Build `hexxu-telemetry` pi extension implementing locked JSONL schema with mode 0600 perms, O_APPEND writes, and the 50MB/90-day rotation policy (~3 hours)
6. Build `hexxu telemetry-summary` CLI (D5.3): reads local JSONL, prints skill/duration/exit-reason summary for `--since <duration>` window (~2 hours)
7. Document `HEXXU_WORKER_ID` setup for the first worker (you): generate a UUID v4, add to shell profile (~10 min)
8. **Test end-to-end with explicit acceptance criteria:**
   - (a) `hexxu/skills` clones cleanly into `~/.pi/agent/skills/` on first pi session
   - (b) cold-start with GitHub unreachable: pi session starts with empty skills + warning (does NOT block)
   - (c) after a session with any skill invoked, at least one JSONL telemetry line lands in the local log with all six locked fields present and 0600 permissions
   - (d) **sync resilience after first success:** with a successful sync as precondition, simulate GitHub unreachable on the next session; pi session uses the cached skills from the successful sync
   - (e) `hexxu telemetry-summary --since 1d` returns the event(s) from (c) with non-zero invocation counts
   - (f) identity drift CI check FAILs a test PR that adds `whoami` to a skill body, and PASSes a clean PR

Total: ~1.5 days with CC (was ~1 day; added ~0.5 days for branch protection setup, identity-drift CI, telemetry CLI, and docs/CONTRIBUTORS scaffolding).
